# PopcornHub — аудит слабых мест

Дата: 2026-11-12

Изучены Go-бэкенд, фронтенд, Docker/compose, README и `plan.md`. Архитектурно код аккуратный: слои `repository → service → handler` разделены, индексы в Mongo создаются, есть JWT, Redis presence, буферизованные WS-каналы, graceful shutdown и базовые тесты. Основные проблемы — в безопасности и надёжности real-time части.

---

## 🔴 Критично

### 1. Цепочка stored XSS → захват аккаунтов

- `web/static/app.js:378`: `<button ... data-room-id="${p.room_id}">` — значение вставляется без экранирования. `room_id` приходит из presence, а `internal/websocket/presence_hub.go:213-229` принимает `SET_STATUS` с произвольными `room_id`, `media_id`, `media_title` от любого авторизованного клиента.
- Событие presence рассылается **всем** подключённым (`presence_hub.go:71-84`), поэтому один пользователь может выполнить JS у всех онлайн-пользователей.
- Также без экранирования вставляются URL: `p.avatar_url` (`app.js:372`), `m.avatar_url` (`452`), `item.poster_url` (`475`, `568`), `u.avatar_url` (`926`). Причём `avatar_url` задаётся при регистрации без валидации (`internal/service/auth_service.go:59-62`), а media может создавать любой пользователь.
- JWT хранится в `localStorage` (`app.js:10-11,158-159`), CSP отсутствует → XSS сразу даёт кражу access/refresh токенов.

**Как исправить:** не собирать HTML конкатенацией; использовать `textContent`/`setAttribute`; валидировать URL на сервере (только http/https) и `room_id` как ObjectID; добавить CSP; в идеале перейти на `HttpOnly`-cookies.

### 2. Refresh-токен принимается как access-токен

`internal/auth/auth.go:93-111` не проверяет тип токена. Refresh-токен подписан тем же секретом и содержит `user_id`, поэтому парсится в `AccessClaims` и проходит `token.Valid`. Итог: 7-дневный refresh можно использовать как обычный Bearer, обходя 15-минутный TTL.

Плюс refresh не ротируется и не отзывается (`auth_service.go:123-147`), logout только чистит localStorage.

**Как исправить:** добавить `token_type: "access"` и проверять его, использовать отдельный ключ/audience, реализовать rotation + jti/blacklist, отзыв при logout.

### 3. Presence уходит всем пользователям и течёт между группами

`presence_hub.go:75-84` рассылает события всем, без фильтра по группе. В payload есть имя, `group_id`, `media_title`, `room_id`. Дополнительно `internal/service/presence_service.go:89-120` не фильтрует по `p.GroupID`: пользователь, состоящий в группах A и B, «светится» в A с фильмом из B.

**Как исправить:** каналы/фильтрация по группам, проверка `GroupID`, отправка дельт только участникам группы.

### 4. Инфраструктура и секреты

- `internal/config/config.go:28` — дефолтный JWT secret, он же лежит в `.env`. Если env не задан, токены можно подделать.
- `docker-compose.yml:22-23,37-38` публикует Mongo `27017` и Redis `6379` наружу без аутентификации. Redis без пароля + presence pub/sub = возможность **неавторизованно публиковать XSS-события всем клиентам**; Mongo — чтение/изменение БД.
- `/metrics` открыт без авторизации (`internal/api/router.go:40`).

**Как исправить:** обязательный секрет с fail-fast при отсутствии, закрыть порты/сеть Docker, включить Redis AUTH и Mongo auth, спрятать metrics за auth/внутренней сетью.

## 🟠 Высокий приоритет

### 5. Любой пользователь может добавлять media

`router.go:61`, `media_handler.go:54-72`: нет роли admin, нет валидации `stream_url`/`poster_url` → poisoning каталога и stored XSS через `poster_url`.

### 6. Нет лимитов тела запроса и валидации полей

Все хендлеры используют `json.NewDecoder(r.Body)` без `http.MaxBytesReader`; пароль от 4 символов (`auth_service.go:50`), email не валидируется, длины строк не ограничены. Нет rate limit на login/register/join → brute-force и enumeration (`auth_handler.go:32-35`).

### 7. Слабые инвайт-коды

4 цифры + предсказуемый префикс из названия группы (`group_service.go:150-175`), без срока жизни и rate limit на join. Коллизия кода возвращает 500 без retry (`group_service.go:41-44`), а `AddMember` содержит check-then-act гонку (`group_repo.go:84-106`).

### 8. Чат и реакции не лимитируются

`room_hub.go:494-525`: сообщение до 8 КБ → флуд и амплификация через Redis.

### 9. Мультиинстанс сломан

`listenRedisRoom` (`room_hub.go:259-272`) только пересылает payload локальным клиентам, но не обновляет `LocalRoom`. Новый клиент на другом инстансе получает устаревший `SYNC_STATE` (`210-222`, `228-257`). Rate limiter тоже in-memory per-instance.

### 10. Локальная доставка зависит от Redis echo

`handleIncomingAction` не рассылает локально, только `broadcastToRedis` (`room_hub.go:468-477`). Если Redis недоступен, даже инициатор не получит PLAY/PAUSE/SEEK/chat; ошибки публикации игнорируются (`352-359`).

### 11. Гонки жизненного цикла комнаты

`unregisterClient` (`room_hub.go:309-350`) читает `room.clients` под `h.mu`, хотя map защищён `room.mu`; новый клиент может зарегистрироваться между проверкой `len==0` и `close(stopChan)/delete` → «призрачная» комната без pub/sub.

### 12. Presence-модель конфликтует с комнатой

TTL 45 с продлевается только presence-сокетом (`presence_hub.go:208-212`), в комнате без presence-таба статус истекает; закрытие presence-таба ставит `idle`, даже если человек смотрит (`146-156`). `active_users` в Mongo не чистится при краше (`room_repo.go:72-88`).

### 13. WebSocket-безопасность и надёжность

- `CheckOrigin` всегда `true` (`presence_hub.go:20-26`).
- Токен в query (`app.js:303,637`) попадает в логи прокси.
- У room-сокета нет reconnect (`app.js:654-657`), presence реконнектится вечно с истёкшим токеном (`326-333`).
- Медленным клиентам молча дропаются критичные PAUSE/SEEK (`361-372`).
- Нет лимита соединений на пользователя/IP.

## 🟡 Средний приоритет

### 14. Playback без валидации

`position_sec` принимается любой — отрицательный, больше длительности, огромный (`room_hub.go:435-454`); `CurrentPosition` не клампится к duration (`51-61`). `server_time` клиент игнорирует (`app.js:678-681`), поэтому синхронизация получает офсет на RTT.

### 15. Mongo и комнаты

- `FindActiveByGroupID` (`room_repo.go:47-59`) возвращает последнюю созданную комнату, хотя «активности» нет; старые комнаты копятся.
- `GetOrCreateRoom` при ошибке БД молча создаёт новую комнату (`room_service.go:49-55`), есть гонка на дубли.
- Асинхронные записи состояния могут переупорядочиваться (`room_hub.go:457-466`).
- Нет TTL/закрытия комнат и лимита размера группы (embedded `members` упрётся в 16 МБ).

### 16. Утечка внутренних ошибок

14 мест отдают `err.Error()` клиенту (`*_handler.go`) с деталями Mongo/Redis.

### 17. Health и observability

`healthz` не проверяет Mongo/Redis (`router.go:31-37`); `LOG_LEVEL` игнорируется (`main.go:26-28`); `SyncLatency` объявлена, но не используется (`metrics.go:42`).

### 18. Кардинальность метрик

Для 404 используется `pattern = r.URL.Path` (`middleware.go:57-60`) → случайные URL создают неограниченное число лейблов и рост памяти.

### 19. Хедеры и API

CORS `*` (`middleware.go:79`), нет CSP/X-Frame-Options/HSTS/nosniff; ошибки middleware отдаются text/plain вместо JSON; нет пагинации для `/groups` и `/media`.

### 20. Продуктовые пробелы

Нет восстановления пароля/верификации email, истории чата, выхода/удаления группы, управления ролями (роль `admin` не используется), пагинации.

### 21. Фронтенд

- Демо-логин и пароль прямо в `index.html:50,55`.
- На каждое presence-событие **всех** пользователей вызывается REST `loadGroupPresence` (`app.js:344-348`) → N² запросов.
- `connStatus` никогда не обновляется.

## 🔵 Гигиена и деплой

### 22. Docker

`Dockerfile` не multi-stage (вопреки `README.md:16`) и копирует уже собранный `server` (`Dockerfile:7`). Бинарник в `.gitignore`, поэтому на чистом клоне `docker compose up --build` упадёт, а локально можно задеплоить устаревший бинарник. Контейнер работает от root, нет `HEALTHCHECK`.

### 23. Тесты и CI

Тесты минимальны: только auth, rate limiter и generateInviteCode. Нет тестов хендлеров, WS-синхронизации, репозиториев, интеграционных тестов и CI. В текущем окружении `go test ./...` не завершился за 3 минуты (при этом `./internal/auth` проходит).

### 24. Прочее

`go.mod` требует Go 1.27.1, README говорит 1.22+; `.env` с секретом лежит локально (в git не попал — хорошо, но легко утечёт); seed-«Интерстеллар» на самом деле указывает на Elephants Dream (`database/mongodb.go:147-149`).

## Что исправлять первым

1. Закрыть XSS: убрать конкатенацию HTML, экранировать все URL и `room_id`, валидировать URL на сервере, добавить CSP; в идеале перейти на `HttpOnly`-cookies.
2. Ввести `token_type` для access/refresh, ротацию и отзыв refresh, обязательный JWT secret; закрыть Redis/Mongo и `/metrics`.
3. Presence: фильтр по группе/`GroupID`, рассылка только участникам, статус из комнаты, а не из отдельного сокета.
4. Ограничить размеры тел запросов и полей, добавить rate limit на auth/join/chat и проверку прав на создание media.
5. Починить надёжность комнат: локальная рассылка + Redis publish, корректные локи жизненного цикла, clamp позиции, reconnect/refresh на клиенте.
