# План разработки сервиса для совместного просмотра контента

Сервис предназначен для синхронного просмотра медиаконтента семьями и дружескими компаниями. Платформа позволяет объединяться в группы, видеть текущую активность участников и в один клик присоединяться к просмотру с открытым (демократичным) управлением плеером.

---

## 1. Архитектурный стек и специфика реализации

* **Язык разработки**: Go (Golang 1.22+).
* **Маршрутизация**: Стандартная библиотека `net/http.ServeMux` (использование встроенного роутинга методов и параметров путей без сторонних веб-фреймворков).
* **Сетевой транспорт реального времени**: WebSockets (`nhooyr.io/websocket` или Gorilla WebSocket).
* **Основная база данных**: MongoDB (официальный драйвер `go.mongodb.org/mongo-driver/v2/mongo`).
* **Кэш и шина событий**: Redis (Pub/Sub для межсервисной рассылки сообщений между инстансами и временного хранения статусов присутствия).
* **Модель управления**: Демократичная (любой подключенный участник группы в комнате может запускать, останавливать и перематывать воспроизведение).

## 2. Модели документов в MongoDB

### Коллекция `users`
```json
{
  "_id": "ObjectId",
  "name": "Иван",
  "email": "ivan@example.com",
  "password_hash": "string",
  "avatar_url": "string",
  "created_at": "ISODate"
}
```

### Коллекция `groups`
```json
{
  "_id": "ObjectId",
  "name": "Семья",
  "invite_code": "FAM-9821",
  "owner_id": "ObjectId(users)",
  "members": [
    {
      "user_id": "ObjectId(users)",
      "role": "owner | admin | member",
      "joined_at": "ISODate"
    }
  ],
  "created_at": "ISODate"
}
```

### Коллекция `media_catalog`
```json
{
  "_id": "ObjectId",
  "title": "Интерстеллар",
  "stream_url": "https://cdn.example.com/streams/interstellar/master.m3u8",
  "duration_sec": 10140,
  "poster_url": "string",
  "metadata": {
    "genre": ["Sci-Fi", "Drama"],
    "year": 2014
  }
}
```

### Коллекция `watch_rooms` (активные комнаты)
```json
{
  "_id": "ObjectId",
  "group_id": "ObjectId(groups)",
  "media_id": "ObjectId(media_catalog)",
  "playback_state": {
    "is_playing": true,
    "position_sec": 1420.5,
    "updated_at": "ISODate",
    "last_action_by": "ObjectId(users)"
  },
  "active_users": ["ObjectId(users)"],
  "created_at": "ISODate"
}
```

## 3. Детальный план разработки (Roadmap)

### Этап 1. Базовый API на net/http и хранилище MongoDB (Недели 1–2)
1. **Слой маршрутизации (`net/http.ServeMux`)**:
   * Настройка стандартного мультиплексора Go 1.22+ (`mux.HandleFunc("POST /api/v1/auth/register", ...)`).
   * Middleware-цепочка: структурированное логирование (`log/slog`), обработка CORS, перехват паник (`recover`), проверка JWT.
2. **Интеграция с MongoDB**:
   * Пул подключений через официальный драйвер.
   * Настройка уникальных индексов на `users.email` и `groups.invite_code`, а также индекса для поиска по `groups.members.user_id`.
3. **Модули аутентификации и групп**:
   * Регистрация, вход, выдача Access/Refresh токенов.
   * Создание группы, генерация инвайт-кода, вступление по коду, просмотр участников группы.

### Этап 2. Сервис присутствия (Presence System — «Кто что смотрит») (Недели 3–4)
1. **WebSocket-шлюз присутствия (`/ws/presence`)**:
   * Постоянное соединение пользователя при нахождении на платформе.
   * Heartbeat-механизм: пинги от клиента каждые 15 секунд с автообновлением TTL в Redis.
2. **Синхронизация статусов**:
   * Хранение текущей активности в Redis (`user:presence:{user_id}`) со структурой: статус (`idle`/`watching`), `media_id`, `room_id`.
   * При старте просмотра пользователем событие транслируется через Redis Pub/Sub согруппникам.
   * В интерфейсе группы динамически отображается карточка: *«Алексей смотрит [Фильм X]»* с кнопкой *«Присоединиться»*.

### Этап 3. Комнаты совместного просмотра с открытым управлением (Недели 5–6)
1. **Жизненный цикл сессии**:
   * Создание комнаты при начале просмотра или переход в открытый режим.
   * Подключение к комнате по адресу `/ws/rooms/{room_id}`.
   * Передача новому участнику текущего таймкода с учетом времени, прошедшего с момента последнего `PLAY`.
2. **Демократический движок синхронизации (Collaborative Playback)**:
   * **Протокол сообщений**:
     * `PLAY` — запуск воспроизведения с указанной позиции.
     * `PAUSE` — остановка на конкретной секунде.
     * `SEEK` — перенос позиции.
     * `SYNC_STATE` — регулярная сверка времени.
   * **Обработка на Go**:
     * Защита состояния комнаты в памяти с помощью `sync.RWMutex` или акторной модели через каналы Go.
     * Любой участник может послать команду управления.
     * Сервер обновляет позицию, сохраняет метку `server_timestamp` и рассылает broadcast-пакет всем участникам:
       ```json
       {
         "type": "SEEK",
         "position_sec": 1205.0,
         "initiated_by_name": "Мария",
         "server_time": 1730000000123
       }
       ```
3. **Коррекция рассинхронизации (Drift Correction)**:
   * Расхождение < 1–2 сек: плеер плавно регулирует скорость (`playbackRate = 1.05` или `0.95`).
   * Расхождение > 2 сек: жесткая перемотка (`video.currentTime = syncTime`).

### Этап 4. Интерактивность и защита от спама (Недели 7–8)
1. **Внутрикоммуникационные функции**:
   * Легковесный текстовый чат комнаты поверх видеопотока.
   * Всплывающие эмодзи-реакции в реальном времени.
   * Системные уведомления в плеере (например, *«Дмитрий поставил на паузу»*).
2. **Rate Limiting и защита от флуда**:
   * Ограничение частоты команд паузы/перемотки (Token Bucket алгоритм) — не более 1 управляющей команды в 1.5–2 секунды от одного пользователя.
   * Изоляция ошибок WebSocket-клиента, чтобы сбой соединения одного участника не влиял на всю комнату.

### Этап 5. Тестирование, оптимизация и развертывание (Недели 9–10)
1. **Тестирование конкурентности**:
   * Прогон юнит- и интеграционных тестов с флагом `-race` для исключения гонок данных при одновременных запросах.
   * Стресс-тестирование WebSocket-соединений и синхронизации через k6.
2. **Деплой и контейнеризация**:
   * Минимальный многоэтапный (multi-stage) Dockerfile на базе `alpine` или `distroless`.
   * docker-compose файл окружения (Go-app, MongoDB, Redis).
   * Метрики Prometheus (число активных сокетов, задержка синхронизации, RPS) и структурированные логи через `log/slog`.
